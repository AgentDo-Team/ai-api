## 0. 이 문서를 읽기 전 알아야 할 개념 (아기 걸음마 버전)

### 0-1. "회원가입/로그인"은 사실 두 가지 일이다

1. **가입/로그인 그 자체** — 이메일·비밀번호를 받아서, 비밀번호를 안전하게 저장하고, 나중에 맞는지 확인하는 일.
2. **"로그인 상태 유지"** — 로그인에 성공한 뒤, *다음 요청*에서도 이 사람이 로그인했다는 걸 어떻게 증명하느냐 하는 일.

우리 프로젝트는 화면(HTML)을 그리는 웹사이트가 아니라 **API 서버**다. API 서버에서 로그인 상태를 유지하는 표준 방법이 바로 **JWT(토큰)** 방식이다.

### 0-2. JWT(Json Web Token)가 뭐냐

- 로그인에 성공하면 서버가 **토큰**이라는 긴 문자열을 하나 만들어 준다.
- 이 토큰 안에는 "이 사람은 3번 사용자이고, 언제까지 유효하다"는 정보가 들어 있고, 마지막에 **서버만 아는 비밀키(SECRET_KEY)로 만든 서명**이 붙는다.
- 클라이언트(프론트/앱)는 이후 모든 요청에 이 토큰을 `Authorization: Bearer <토큰>` 헤더로 같이 보낸다.
- 서버는 토큰의 서명을 비밀키로 검사해서 "위조 안 됐네, 우리가 발급한 거 맞네"를 확인한다.
- **핵심 장점**: 서버가 "누가 로그인 중인지"를 따로 기억(저장)할 필요가 없다. 토큰 자체가 신분증 역할을 한다.

토큰은 점(`.`) 두 개로 나뉜 3덩어리 구조다: `헤더.내용(payload).서명`.
- 헤더: "이거 JWT고 HS256으로 서명했어"
- payload: 실제 정보 (우리는 `sub`=사용자id, `exp`=만료시각을 담음)
- 서명: 비밀키로 만든 위조 방지 도장

> ⚠️ payload는 암호화가 아니라 **인코딩(Base64)**일 뿐이라 누구나 열어볼 수 있다. 그래서 비밀번호 같은 민감정보는 절대 토큰에 넣지 않는다. 우리는 사용자 id만 넣었다.

### 0-3. 비밀번호는 왜 "해싱"하나

- 비밀번호를 DB에 **그대로(평문) 저장하면 절대 안 된다.** DB가 유출되면 모든 사용자의 비밀번호가 그대로 털린다.
- 그래서 **bcrypt**라는 해시 함수로 비밀번호를 알아볼 수 없는 문자열로 바꿔서 저장한다.
  - 예: `password123` → `$2b$12$KPMdd6sLHsMYlehLdKU4yu...`
- 해시는 **한 방향**이다. 비밀번호 → 해시는 되지만, 해시 → 비밀번호는 되돌릴 수 없다.
- 로그인할 때는? 입력한 비밀번호를 다시 해싱해서 저장된 해시와 비교(`checkpw`)한다. bcrypt는 이 비교를 알아서 해준다.
- bcrypt는 일부러 **느리게** 설계돼 있어서, 해커가 무차별 대입으로 비밀번호를 맞춰보기 어렵게 만든다. (`$12$` 부분이 그 강도)

## 1. 전체 그림 (요청이 흐르는 순서)

```
[클라이언트]
    │  POST /auth/signup  {email, password}
    ▼
[auth.py 라우터]  ──▶  [auth_service.signup]  ──▶  [security.hash_password]
    │                        │                          (bcrypt로 해싱)
    │                        ▼
    │                   [DB: users 테이블에 저장]
    ▼
  200 OK {id, email, created_at}


[클라이언트]
    │  POST /auth/login  {email, password}
    ▼
[auth.py 라우터]  ──▶  [auth_service.login]  ──▶  [security.verify_password]
    │                        │                          (해시 비교)
    │                        └──▶ [security.create_access_token]  (JWT 발급)
    ▼
  200 OK {access_token}


[클라이언트]
    │  GET /auth/me   Authorization: Bearer <토큰>
    ▼
[auth.py: get_current_user 의존성]  ──▶  [security.decode_access_token]
    │                                          (서명·만료 검증 → 사용자 id 추출)
    │                                          ──▶ [DB: 그 id의 사용자 조회]
    ▼
  200 OK {내 정보}
```

계층을 나눈 이유(뒤에서 자세히): **라우터(HTTP 담당) → 서비스(비즈니스 로직) → security(순수 계산) / DB(저장)** 로 역할을 분리해서, 각 부분을 따로 이해하고 따로 테스트할 수 있게 했다.

## 2. 새로 생성한 파일 (코드 한 줄씩 해설)

### 2-1. `app/db/models/user.py` — 사용자 테이블 정의

DB의 `users` 테이블이 어떻게 생겼는지를 파이썬 클래스로 적은 것이다. (SQLModel = SQLAlchemy ORM + Pydantic)

```python
from datetime import datetime
from sqlalchemy import BigInteger, Column, DateTime, String, func
from sqlmodel import Field, SQLModel


class User(SQLModel, table=True):
    __tablename__ = "users"

    id: int | None = Field(
        default=None,
        sa_column=Column(BigInteger, primary_key=True, autoincrement=True),
    )
    email: str = Field(
        sa_column=Column(String(255), unique=True, nullable=False),
    )  # 로그인 이메일 (중복 불가)
    hashed_password: str = Field(
        sa_column=Column(String(255), nullable=False),
    )  # bcrypt 해시 (평문 저장 금지)
    created_at: datetime | None = Field(
        default=None,
        sa_column=Column(DateTime(timezone=True), server_default=func.now(), nullable=False),
    )
```

한 줄씩:
- `class User(SQLModel, table=True)`: `table=True`는 "이건 진짜 DB 테이블이야"라는 표시. (이게 없으면 그냥 데이터 형태만 정의하는 스키마가 된다.)
- `__tablename__ = "users"`: DB에 만들어질 테이블 이름.
- `id`: 사용자 고유 번호. `primary_key=True`(기본키), `autoincrement=True`(1, 2, 3... 자동 증가). `BigInteger`는 아주 큰 정수 타입. `default=None`인 이유는, **저장하기 전엔 id가 없고 DB가 저장할 때 번호를 매기기 때문**이다.
- `email`: `String(255)`(최대 255자), `unique=True`(**같은 이메일로 두 번 가입 못 함** — DB 차원의 안전장치), `nullable=False`(비어 있으면 안 됨).
- `hashed_password`: 비밀번호를 **해싱한 결과**를 저장. 이름에 `hashed_`를 붙여서 "여긴 평문이 아니라 해시가 들어간다"를 코드만 봐도 알게 했다.
- `created_at`: 가입 시각. `server_default=func.now()`는 "값을 안 줘도 **DB가 현재 시각을 자동으로** 넣어줘"라는 뜻. `timezone=True`로 시간대 정보까지 저장.

> 이 파일의 컬럼 정의 스타일(BigInteger PK, server_default=func.now())은 프로젝트의 기존 모델(`company.py`, `analysis.py`)과 **완전히 동일한 패턴**을 따랐다. 혼자 튀는 코드를 만들지 않으려고.

### 2-2. `app/core/security.py` — 보안 계산 유틸 (순수 함수 모음)

비밀번호 해싱과 JWT 발급/검증처럼 **"DB도 HTTP도 모르는 순수한 계산"**만 모아둔 파일. 이렇게 떼어두면 어디서든 갖다 쓰고 따로 테스트하기 쉽다.

```python
from datetime import UTC, datetime, timedelta
import bcrypt
import jwt
from app.core.config import settings


def hash_password(password: str) -> str:
    hashed = bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt())
    return hashed.decode("utf-8")
```
- `password.encode("utf-8")`: bcrypt는 문자열이 아니라 **바이트**를 다루므로 먼저 바이트로 변환.
- `bcrypt.gensalt()`: **소금(salt)**을 생성. 소금은 매번 랜덤이라, *같은 비밀번호라도 저장되는 해시가 매번 다르다.* 덕분에 "미리 계산해둔 해시표(레인보우 테이블)"로 뚫는 공격을 막는다.
- `bcrypt.hashpw(...)`: 비밀번호 + 소금 → 최종 해시(바이트).
- `.decode("utf-8")`: 바이트를 다시 문자열로 바꿔서 DB(문자열 컬럼)에 저장할 수 있게 함.

```python
def verify_password(password: str, hashed_password: str) -> bool:
    return bcrypt.checkpw(
        password.encode("utf-8"), hashed_password.encode("utf-8")
    )
```
- 로그인할 때 쓴다. 입력 비밀번호와 저장된 해시를 넣으면 **bcrypt가 알아서** "소금을 뽑아내 다시 해싱 → 비교"까지 해주고 `True/False`를 준다. 우리가 직접 해시를 다시 만들 필요가 없다.

```python
def create_access_token(subject: str | int) -> str:
    expire = datetime.now(UTC) + timedelta(
        minutes=settings.access_token_expire_minutes
    )
    payload = {"sub": str(subject), "exp": expire}
    return jwt.encode(payload, settings.secret_key, algorithm=settings.jwt_algorithm)
```
- `subject`: 토큰의 주인 = 사용자 id.
- `expire`: **지금 시각 + 만료(분)** → 이 시각이 지나면 토큰이 자동으로 무효가 된다. 기본 60분(설정값).
- `datetime.now(UTC)`: 시간대를 UTC로 명확히 지정. (서버/DB 시간대가 달라도 헷갈리지 않게.)
- `payload`: 토큰에 담을 내용. `sub`(주체)와 `exp`(만료)는 JWT 표준 필드 이름이다. `str(subject)` — id를 문자열로 넣는 이유는 JWT `sub`가 문자열이어야 한다는 규약 때문.
- `jwt.encode(payload, 비밀키, 알고리즘)`: payload를 비밀키로 서명해서 토큰 문자열을 만든다.

```python
def decode_access_token(token: str) -> dict:
    return jwt.decode(
        token, settings.secret_key, algorithms=[settings.jwt_algorithm]
    )
```
- 토큰을 **검증하면서** 열어본다. 비밀키로 서명이 맞는지, `exp`가 안 지났는지 자동으로 확인한다.
- 서명이 틀리거나(위조) 만료됐으면 `jwt.PyJWTError` 예외를 던진다 → 이 예외는 라우터(`get_current_user`)에서 잡아 401로 바꾼다.

### 2-3. `app/schemas/auth.py` — 요청/응답 데이터 형태(스키마)

API가 **받는 데이터**와 **주는 데이터**의 모양을 정의한다. Pydantic이 이 정의를 보고 자동으로 검증해준다.

```python
from datetime import datetime
from pydantic import BaseModel, EmailStr, Field


class SignupRequest(BaseModel):
    email: EmailStr
    password: str = Field(min_length=8, max_length=72)


class LoginRequest(BaseModel):
    email: EmailStr
    password: str


class UserResponse(BaseModel):
    id: int
    email: EmailStr
    created_at: datetime


class TokenResponse(BaseModel):
    access_token: str
    token_type: str = "bearer"
```

- `EmailStr`: "진짜 이메일 형식인지" 자동 검증. `abc`처럼 `@`가 없으면 요청 단계에서 바로 걸러진다. (이 타입 때문에 `email-validator` 패키지를 설치했다.)
- `password: Field(min_length=8, max_length=72)`:
  - `min_length=8` — 너무 짧은 비밀번호 방지(최소한의 정책).
  - `max_length=72` — **bcrypt는 72바이트까지만 처리**하는 한계가 있어서, 그보다 길게 받아봤자 뒤는 잘린다. 그래서 입력 단계에서 막았다. (설계 고민 4-4 참고)
- `UserResponse`에는 **`hashed_password`가 없다.** 응답으로 비밀번호 해시를 절대 내보내지 않기 위해, 내보내도 되는 필드(`id/email/created_at`)만 따로 정의했다. (설계 고민 4-2)
- `TokenResponse.token_type = "bearer"`: OAuth2 표준에 따라 "이 토큰은 Bearer 방식으로 쓰세요"를 알려주는 관례적 필드.

### 2-4. `app/services/auth_service.py` — 비즈니스 로직

"가입이면 중복 검사 후 저장", "로그인이면 검증 후 토큰 발급" 같은 **실제 규칙**이 있는 곳. HTTP나 응답 포맷은 여기서 신경 쓰지 않고 순수하게 로직만 담당한다.

```python
async def signup(session: AsyncSession, data: SignupRequest) -> User:
    existing = await session.scalar(select(User).where(User.email == data.email))
    if existing is not None:
        raise AppException("이미 가입된 이메일입니다.", status_code=409)

    user = User(
        email=data.email,
        hashed_password=hash_password(data.password),
    )
    session.add(user)
    await session.commit()
    await session.refresh(user)
    return user
```
- `select(User).where(User.email == data.email)`: "이 이메일을 쓰는 사용자가 이미 있나?" 조회.
- `session.scalar(...)`: 결과에서 첫 값 하나를 꺼냄. 있으면 그 User 객체, 없으면 `None`.
- 이미 있으면 → `AppException(..., 409)`. **409 Conflict**는 "리소스 충돌(중복)"을 뜻하는 HTTP 상태코드.
- 없으면 → 비밀번호를 **해싱해서**(`hash_password`) User 객체를 만들고,
- `session.add()` → `commit()`(DB에 확정 저장) → `refresh()`(방금 DB가 매긴 `id`, `created_at`을 다시 읽어와 객체를 채움).

> `await`가 붙는 이유: 이 프로젝트는 **비동기(async) DB 세션**을 쓴다. DB 작업은 시간이 걸리므로, 기다리는 동안 서버가 다른 요청을 처리할 수 있게 `async/await`로 처리한다. (기존 `session.py`의 방식을 그대로 따름.)

```python
async def login(session: AsyncSession, data: LoginRequest) -> str:
    user = await session.scalar(select(User).where(User.email == data.email))
    if user is None or not verify_password(data.password, user.hashed_password):
        raise AppException("이메일 또는 비밀번호가 올바르지 않습니다.", status_code=401)

    return create_access_token(subject=user.id)
```
- 이메일로 사용자를 찾고, 비밀번호를 검증한다.
- **중요한 설계**: 이메일이 없든 비밀번호가 틀리든 **똑같은 메시지**(`이메일 또는 비밀번호가 올바르지 않습니다.`)와 **똑같은 401**을 준다. → "이 이메일은 가입돼 있구나(비번만 틀림)"라는 힌트를 공격자에게 주지 않기 위함. (설계 고민 4-3)
- `if user is None or not verify_password(...)`: 파이썬은 앞이 참이면 뒤를 안 본다(단락 평가). 그래서 `user`가 없으면 `user.hashed_password`에 접근하지 않아 에러가 안 난다.
- 통과하면 → 그 사용자 id로 JWT 토큰을 만들어 **문자열로** 반환.

### 2-5. `app/api/auth.py` — HTTP 라우터 (엔드포인트)

바깥세상(HTTP 요청)과 맞닿는 부분. 요청을 받아 서비스에 넘기고, 결과를 공통 응답 포맷으로 감싸서 돌려준다.

```python
router = APIRouter(prefix="/auth", tags=["auth"])
oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")
```
- `APIRouter(prefix="/auth")`: 이 파일의 모든 경로 앞에 `/auth`가 붙는다 → `/auth/signup`, `/auth/login`, `/auth/me`.
- `tags=["auth"]`: 자동 생성되는 API 문서(`/docs`)에서 auth 그룹으로 묶어 보여준다.
- `OAuth2PasswordBearer(tokenUrl="/auth/login")`: 요청 헤더에서 `Authorization: Bearer <토큰>`을 **꺼내주는 도우미**. `tokenUrl`은 "토큰은 여기서 발급받아요"라는 문서용 정보(=`/docs`의 Authorize 버튼과 연결). 토큰이 아예 없으면 이 도우미가 자동으로 401을 낸다.

```python
@router.post("/signup")
async def signup(data: SignupRequest, session: AsyncSession = Depends(get_session)) -> ApiResponse[UserResponse]:
    user = await auth_service.signup(session, data)
    return ApiResponse.ok(
        data=UserResponse.model_validate(user, from_attributes=True),
        message="회원가입이 완료되었습니다.",
    )
```
- `data: SignupRequest`: 요청 본문(JSON)을 자동으로 `SignupRequest`로 파싱+검증. 이메일 형식/비번 길이가 안 맞으면 여기서 자동 422.
- `session: ... = Depends(get_session)`: **의존성 주입.** FastAPI가 요청마다 DB 세션을 자동으로 열어서 넣어주고, 끝나면 닫아준다. 우리가 직접 세션을 만들 필요 없음.
- `UserResponse.model_validate(user, from_attributes=True)`: DB에서 받은 `User` 객체(해시 포함)를 **안전한 `UserResponse`(해시 제외)로 변환**. `from_attributes=True`는 "객체의 속성에서 값을 읽어와라"는 뜻.
- `ApiResponse.ok(...)`: 프로젝트 공통 응답 포맷 `{success, message, data}`로 감싸기. (기존 `schemas/response.py` 재사용 — 새 포맷을 만들지 않고 있는 걸 따랐다.)

```python
async def get_current_user(
    token: str = Depends(oauth2_scheme),
    session: AsyncSession = Depends(get_session),
) -> User:
    credentials_error = AppException("인증 정보가 유효하지 않습니다.", status_code=401)
    try:
        payload = decode_access_token(token)
        user_id = payload.get("sub")
    except jwt.PyJWTError as exc:
        raise credentials_error from exc

    if user_id is None:
        raise credentials_error

    user = await session.get(User, int(user_id))
    if user is None:
        raise credentials_error
    return user
```
- 이게 **"로그인한 사용자만 접근"**을 만드는 핵심 부품이다. 보호하고 싶은 어떤 API든 `current_user = Depends(get_current_user)`만 붙이면 자동으로 인증이 걸린다.
- 흐름: 헤더에서 토큰 꺼냄 → `decode_access_token`으로 서명·만료 검증 → payload에서 `sub`(사용자 id) 추출 → 그 id의 사용자를 DB에서 조회 → 있으면 반환.
- **실패는 전부 같은 401 하나로**: 토큰이 깨졌든, 만료됐든, `sub`가 없든, 그 사용자가 (탈퇴 등으로) DB에 없든 → 모두 "인증 정보가 유효하지 않습니다." 401. 공격자에게 어느 단계에서 막혔는지 알려주지 않기 위해.
- `raise ... from exc`: 원래 예외(exc)를 원인으로 연결해서 로그 추적을 쉽게 함.

```python
@router.get("/me")
async def me(current_user: User = Depends(get_current_user)) -> ApiResponse[UserResponse]:
    return ApiResponse.ok(
        data=UserResponse.model_validate(current_user, from_attributes=True),
    )
```
- 토큰이 유효할 때 내 정보를 돌려주는 엔드포인트. **인증이 실제로 되는지 확인하는 용도**이자, 앞으로 만들 "로그인 필요" API들의 본보기(템플릿) 역할.

### 2-6. `app/api/__init__.py`, `app/services/__init__.py` — 빈 파일

- 내용이 없는 빈 파일이지만 **꼭 필요하다.** 이 파일이 있어야 파이썬이 `app/api`, `app/services` 폴더를 "import 가능한 패키지"로 인식한다.
- 원래 이 폴더들엔 `.gitkeep`(빈 폴더를 git에 올리기 위한 표시)만 있었고 `__init__.py`가 없어서, `from app.services import auth_service` 같은 import가 안정적으로 되게 하려고 추가했다.

## 4. 설계할 때 한 고민과 결정 이유

### 4-1. 왜 계층을 라우터 / 서비스 / security로 나눴나
- **라우터(`api/auth.py`)**: HTTP만 담당 (요청 파싱, 응답 포맷팅).
- **서비스(`services/auth_service.py`)**: "중복이면 막고, 틀리면 401" 같은 규칙만 담당.
- **security(`core/security.py`)**: 해싱·토큰 같은 순수 계산만 담당.
- 이렇게 나누면 ① 각 파일이 짧고 한 가지 일만 해서 이해하기 쉽고, ② security 함수는 DB 없이도 단독 테스트가 되고, ③ 나중에 "카카오 로그인 추가" 같은 변경이 와도 영향 범위가 좁아진다. 그리고 이건 **프로젝트가 이미 쓰던 구조**(공고 검색 기능이 service/api로 나뉘어 있음)와도 일치한다.

### 4-2. 응답에서 비밀번호 해시를 어떻게 숨겼나
- DB 모델(`User`)에는 `hashed_password`가 있지만, **응답 스키마(`UserResponse`)에는 일부러 넣지 않았다.** `model_validate`로 변환하는 순간 `UserResponse`에 정의된 필드만 남아서 해시는 자연스럽게 빠진다. → "실수로 민감정보가 새어나가는 것"을 구조적으로 차단.

### 4-3. 로그인 실패 메시지를 왜 하나로 통일했나
- "없는 이메일"과 "틀린 비밀번호"를 다른 메시지로 주면, 공격자가 **어떤 이메일이 가입돼 있는지 알아낼 수 있다**(계정 존재 여부 노출 = user enumeration). 그래서 둘 다 똑같이 401 + 같은 문구로 통일했다.

### 4-4. 비밀번호 길이를 왜 8~72로 잡았나
- 최소 8자: 너무 쉬운 비밀번호를 막는 최소한의 정책.
- 최대 72자: **bcrypt의 기술적 한계.** bcrypt는 입력의 앞 72바이트만 사용한다. 그보다 길면 뒷부분이 조용히 무시되어 "긴 비밀번호인데 사실은 앞부분만 검사"되는 혼란이 생긴다. 그래서 입력 단계에서 아예 72자로 제한해 오해의 소지를 없앴다.

### 4-5. 왜 리프레시 토큰 없이 액세스 토큰만? (최소 구성)
- 요구사항이 "가장 기본이 되는 회원가입/로그인"이었다. 리프레시 토큰(토큰 자동 갱신), 로그아웃 블랙리스트, 이메일 인증, 비밀번호 재설정 등은 **나중에 필요할 때 얹는** 확장 기능으로 두고, 지금은 핵심 흐름만 깔끔하게 세웠다.

### 4-6. passlib 대신 bcrypt를 직접 쓴 이유
- FastAPI 튜토리얼은 보통 `passlib[bcrypt]`를 쓰지만, 최신 `bcrypt`(4.x/5.x)와 `passlib`(1.7.4) 사이에 호환 경고(`AttributeError: module 'bcrypt' has no attribute '__about__'`)가 뜨는 알려진 문제가 있다. 우리는 `bcrypt`를 **직접** 호출해서 이 잡음을 없애고 의존성도 하나 줄였다. (`hashpw`/`checkpw` 두 함수면 충분.)

## 5. 트러블슈팅 (실제로 겪은 문제들)

### 5-1. "라우터를 등록했는데 경로가 안 보인다" (알고 보니 정상)
- **증상**: `app.include_router(auth_router)` 후 `app.routes`를 출력했는데 `/auth/*`가 안 보이고, 대신 `_IncludedRouter`라는 낯선 객체 하나만 있었다.
- **원인**: 이 프로젝트의 FastAPI 버전(0.139+)은 라우터를 **지연(lazy) 방식**으로 포함한다. 예전처럼 하위 경로들을 평평한 리스트에 곧바로 펼치지 않고, `_IncludedRouter` 래퍼 하나로 담아뒀다가 요청 시점에 해석한다. 즉 **경로는 정상 등록돼 있었고, 내 확인 방법이 옛날 방식이었다.**
- **해결**: `app.routes`를 세는 대신 `app.openapi()["paths"]`(실제 문서에 잡히는 경로)로 확인 → `['/auth/signup', '/auth/login', '/auth/me', '/', '/health']` 정상 확인. 이후엔 아예 실제 HTTP 요청으로 검증.

### 5-2. SQLite로 빠르게 테스트하려다 실패
- **증상**: DB 없이 빠르게 검증하려고 인메모리 SQLite에 `users` 테이블만 만들었더니 `NOT NULL constraint failed: users.id` 에러.
- **원인**: 모델의 기본키가 `BigInteger + autoincrement`인데, **SQLite는 `BIGINT` 컬럼을 자동 증가시키지 못한다**(SQLite는 `INTEGER PRIMARY KEY`만 자동 증가). PostgreSQL에서는 완전히 정상 동작하는 표준 패턴이라, 이건 **코드 버그가 아니라 SQLite의 한계**였다.
- **해결**: 대충 우회하지 않고, 실제 대상 DB인 **PostgreSQL로 검증**하기로 결정. Docker로 진짜 DB를 띄웠다. (참고로 이 과정에서 bcrypt 해싱과 `/auth/signup` 라우팅은 이미 정상 동작함을 로그로 확인.)

### 5-3. Docker Desktop이 꺼져 있었음
- **증상**: `docker ps` 실행 시 `failed to connect to the docker API ... daemon` 에러.
- **해결**: Docker Desktop을 실행 → 데몬이 뜰 때까지 대기 → `docker compose up -d`로 postgres 컨테이너 기동 → healthcheck가 `healthy`가 될 때까지 대기 후 진행.

### 5-4. DB 초기화 스크립트가 Windows 콘솔에서 크래시 (기존 코드 이슈)
- **증상**: `python -m app.db.init_db` 실행 끝에 `UnicodeEncodeError: 'cp949' codec can't encode character '✅'`.
- **원인**: `init_db.py` 마지막 줄 `print("✅ DB 스키마 초기화 완료")`의 이모지를 Windows 기본 콘솔 인코딩(cp949)이 출력하지 못함. **테이블 생성 자체는 이 print 이전에 이미 끝나서 성공**했고, 마지막 출력에서만 터진 것.
- **임시 해결**: 실행 시 `PYTHONIOENCODING=utf-8`(또는 `PYTHONUTF8=1`) 환경변수를 주면 정상 출력.
- **참고(이번 범위 밖)**: 이 프로젝트가 Windows에서 돌아가는 만큼, `init_db.py`의 이모지/한글 print를 손보면 근본 해결됨. 이번 작업(인증)과 무관해서 건드리지 않았다.

| 7 | 정상 토큰으로 `/auth/me` | 200, 내 이메일 반환 | ✅ 200 |

### 7-3. 확인된 것
- 비밀번호가 **평문이 아니라 bcrypt 해시**(`$2b$12$...`)로 저장됨.
- 응답에 **`hashed_password`가 절대 포함되지 않음**.
- JWT가 정상 발급되고, 그 토큰으로 보호된 엔드포인트(`/auth/me`)에 접근 가능.
- 위조/누락 토큰은 모두 401로 차단.

### 7-4. 아직 자동화 테스트로 남기진 않음
- 이번 검증은 일회성 스크립트로 돌리고 지웠다(scratchpad). 다음 작업으로 `tests/`에 **pytest 통합 테스트**로 옮겨 CI에서 매번 자동 검증되게 하면 좋다.
